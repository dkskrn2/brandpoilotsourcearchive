# Brand Pilot Monorepo and Split Deployment Design

## Goal

Move the complete Brand Pilot codebase into `dkskrn2/main` under `brand_poilot/`, make that directory the only active development source, and deploy the existing website, customer application, and Ubuntu services through independent release paths.

## Confirmed Initial-Migration Scope (2026-07-23)

The operator confirmed that Brand Pilot is still an internal pilot: there are no external customers and no continuity-critical Instagram DM or webhook deliveries. This decision is authoritative for the first Ubuntu migration and supersedes any broader first-release language below.

The initial migration therefore consists only of preserving and importing the canonical source, restoring deterministic build/test gates, applying the minimum Ubuntu runtime hardening, publishing an immutable API image, performing an API-only dark deployment, moving the stable API DNS target, and then activating DM/Wiki workers one at a time after observation. A short announced maintenance window is acceptable. The existing Vercel API is retained as a rollback target for 24–48 hours and is not deleted during the migration.

The following work is explicitly deferred to separately reviewed releases: public customer launch, private-object-store conversion, OAuth/session/worker-principal schema redesign, model-worker runtime redesign, maintenance timer/service, scheduler or Instagram publication activation, legacy Vercel project deletion, and the callback-only receiver/two-floor cutover ledger. Those controls remain relevant before external-customer launch, but they are not prerequisites for proving the internal-pilot API on Ubuntu.

The executable initial-migration sequence is split into two plans:

- ../plans/2026-07-23-brand-pilot-repository-and-api-hardening.md
- ../plans/2026-07-23-brand-pilot-ubuntu-api-deployment.md

## Decisions

- `dkskrn2/main` becomes the canonical repository for the website, administrator UI, Brand Pilot customer UI, API, workers, database migrations, and deployment configuration.
- The existing `brandpoilotsourcearchive` repository remains historical storage. Commit `ec40164` must be pushed to a named archive branch or tag before the monorepo migration is merged so the recorded source revision stays reachable.
- The current Next.js website remains at the repository root and continues serving `www.danbammsg.co.kr`.
- The current Vite customer application remains unchanged in framework and receives its own Vercel project at `app.danbammsg.co.kr`.
- The Ubuntu first release runs Caddy and the API only, with scheduler and all publication disabled. After the API passes dark-deploy, reboot, rollback, login, and webhook smoke tests, one DM worker is activated, observed, and followed by the second DM worker and Wiki worker. Image, video, card-news, blog, marketing, and other generation workers remain on their current worker machines.
- The tested Ubuntu baseline is Ubuntu 24.04 LTS on `linux/amd64`, which matches the current Intel server. Bootstrap fails before deployment if the host architecture or Docker Compose capability does not match the published images.
- Supabase PostgreSQL and the existing object backend remain in place for the initial migration. Private-object-store conversion is a later public-launch security release. The development-only root `docker-compose.yml`, which currently starts only PostgreSQL, is not reused as the production Compose file.
- No database schema change is performed during repository consolidation or the first Ubuntu cutover. Authentication/session/worker-principal, credential provenance, private-artifact, and maintenance-state changes are separate security releases with their own backup-restore rehearsal and rollback compatibility proof.
- Instagram Login and the Facebook Login flow used by trend search receive separate Meta application credentials. Meta's current App Review documentation says one app can use Instagram Login or Facebook Login, but not both; the current shared `META_APP_ID` and `META_APP_SECRET` production contract is therefore removed before launch.
- Production inference over customer-controlled input—including DM/Wiki, brand intelligence, subject analysis, card news, blog, and marketing—does not spawn a general-purpose Codex CLI with worker credentials. The default release uses tool-less, schema-constrained model API calls so messages, uploaded documents, crawled text, and brand context cannot invoke shell/filesystem/network tools or read DB, worker, Blob, model, or API credentials. Retaining any CLI path requires a separate approved isolation design and adversarial proof.
- Generation workers remain on their current PCs in the first infrastructure release, but that location is not a security exemption. Their model boundary, explicit child environment, uploader separation, credentials, and update procedure must pass the same public-launch gate before customer access opens. A narrowly dedicated image-generation child may keep only its image tool after it proves shell/general network absence and receives no worker or storage token.
- The existing Vercel API remains active while `api.danbammsg.co.kr` is established as the stable API hostname and the customer UI plus Kakao/Meta callback configuration are tested against it. The Ubuntu cutover changes the DNS target only, inside a short maintenance window. The old Vercel API remains intact for 24–48 hours so rollback is a DNS reversal rather than a destructive project restoration. A callback-only receiver, two-floor cutover ledger, writer fencing, and legacy-project deletion are unnecessary for this no-external-customer migration and remain deferred.
- The first public customer release keeps both the local scheduler and Instagram publication disabled. Current disabled publication code can still consume a due row as mock-published, so the scheduler is activated only in a later independent release after disabled-mode zero-mutation behavior, approved private-to-public promotion, one-scheduler ownership, a seeded due-row smoke test, and rollback all pass.
- Delivery is staged: source and customer Preview first, restricted Ubuntu/API-DNS validation second, and provider plus customer traffic promotion last.

## Deployment Boundaries

### Website and administrator UI

- Framework: Next.js.
- Vercel Root Directory: repository root.
- Production domain: `www.danbammsg.co.kr`.
- Existing build, environment variables, administrator authentication, PostgreSQL content integration, SEO metadata, and routes remain intact.
- The currently used `https://www.danbammsg.co.kr/admin/brandpoilot` legacy address remains valid and redirects to the canonical `/admin/brand-pilot`; deployment smoke-tests both so existing bookmarks do not break.
- The website package does not declare `brand_poilot` as an npm workspace, so root dependency installation does not install Brand Pilot packages. That alone does not isolate builds: the current root `tsconfig.json` includes every `**/*.ts(x)` file and root ESLint runs `eslint .`. Import therefore adds `brand_poilot/**` to the root TypeScript exclude and ESLint global ignores, adds a global Next `outputFileTracingExcludes` rule for that subtree, and prohibits root website imports from it. A boundary fixture and trace test prove root typecheck/lint/build remain independent while Brand Pilot runs its own package-local checks.
- The existing website project skips a deployment when a commit changes only `brand_poilot/`. The skip rule is versioned and tested instead of relying on a dashboard-only command.
- After the Ubuntu API is healthy, `BRAND_PILOT_ADMIN_API_URL=https://api.danbammsg.co.kr` and the matching service token are set in the website Vercel project.

### Customer application

- Framework: Vite with React Router.
- Vercel Root Directory: `brand_poilot`. This keeps `package-lock.json` and npm workspace resolution inside the project root.
- Production domain: `app.danbammsg.co.kr`.
- Install command: `npm ci`.
- Build command: `npm run build --workspace @brand-pilot/customer-ui`.
- Output directory: `apps/customer-ui/dist`.
- `brand_poilot/vercel.json` owns the build settings, SPA fallback, security headers, and `X-Robots-Tag: noindex, nofollow, noarchive`.
- Production builds fail when `VITE_API_BASE_URL` is absent or is a localhost URL.
- The production Vercel values are `VITE_API_BASE_URL=https://api.danbammsg.co.kr`, `VITE_META_OAUTH_START_URL=https://api.danbammsg.co.kr/auth/meta/start`, and `VITE_META_TRENDS_CONNECT_URL=https://api.danbammsg.co.kr/auth/meta/trends/start`. The two start-URL variables may be omitted only when their checked fallback is derived from the same production API base.
- React Router pages use route-level lazy loading. The login and application shell stay in the entry chunk; page modules load on demand.
- A checked bundle budget prevents the entry JavaScript from returning to the current 618.87 kB uncompressed single chunk.
- The root path preserves the existing anonymous redirect to the Danbam website. The internal Kakao entry remains available at `/login`; changing that product behavior is outside this migration.
- Production login errors use host-neutral recovery copy. The current message that tells every failed user to retry on `localhost` is retained only for a detected local-origin mismatch and never appears on `app.danbammsg.co.kr`.

Official Vercel behavior supports separate projects with a configured Root Directory, versioned `buildCommand` and `outputDirectory`, and an SPA rewrite to `index.html`. The implementation follows those platform primitives instead of a custom proxy.

### Ubuntu services

- The production path reuses `brand_poilot/docs/superpowers/specs/2026-07-22-ubuntu-container-deployment-design.md` rather than replacing it.
- GitHub Actions builds the API, DM/Wiki, and dedicated non-publishing maintenance images, publishes commit-SHA tags to GHCR, and adds `stable` only after the default-branch build succeeds. Tags are discovery aids; deployment pins immutable image digests and verifies their OCI source-revision labels.
- Ubuntu uses a sparse checkout for `brand_poilot/deploy/`, loads a release manifest that binds the Git SHA, API and worker image digests, Compose/Caddy revision, and environment-schema version, and does not build application source on the server.
- `brand_poilot/deploy/compose.production.yml` runs digest-pinned Caddy, the API, two DM workers, and one Wiki worker and defines the non-public `credential-maintenance` one-shot service invoked only by the host systemd timer. It does not run PostgreSQL. The upstream Caddy digest is a release artifact just like the in-repository image digests, though only in-repository images carry the repository source-revision label.
- Caddy exposes only ports 80 and 443 and routes `https://api.danbammsg.co.kr` to the private API container.
- Worker containers remain private and do not expose host ports.
- Compose sets unique stable identities explicitly: `WORKER_ID=ubuntu-dm-1`, `ubuntu-dm-2`, and `ubuntu-wiki-1`. Startup validation rejects a missing or duplicate ID instead of accepting the PID-based fallback that would collide when multiple containers run as PID 1.
- Supabase PostgreSQL, the dedicated private-storage Supabase project, and the independent public publication backend remain external dependencies.
- Direct Caddy ingress requires a usable public IP, router forwarding for TCP 80/443, and DNS pointing to that endpoint. Bootstrap records the public-IP, static-versus-dynamic status, and CGNAT check. A dynamic public IP requires a tested DNS-provider updater; no public IP or CGNAT stops the rollout with guidance. Switching to an outbound tunnel is a separate reviewed deployment variant, not an implicit fallback.
- The first release has one API replica. Replacing or rolling back that container can cause a short, measured outage; zero-downtime claims are not made. The deployment script keeps the prior release manifest and automatically attempts a bounded full-manifest rollback when the new health check fails.

## Request and Authentication Flow

```text
Browser
  ├── www.danbammsg.co.kr ──> Vercel Next.js website
  │                                └── server-side admin request ─┐
  └── app.danbammsg.co.kr ──> Vercel Vite customer UI            │
                                   └── credentialed HTTPS request ├──> api.danbammsg.co.kr
                                                                  │          │
                                                                  │          ├──> Supabase PostgreSQL
                                                                  │          ├──> isolated private storage / public publication backend
                                                                  │          └──> worker queues
                                                                  └──────────┘

GitHub main commit
  ├──> Vercel website project
  ├──> Vercel customer project
  └──> GitHub Actions ──> GHCR images ──> Ubuntu deployment by release manifest and digests
```

The production API allowlist contains exactly `https://app.danbammsg.co.kr`; the server-side administrator integration is authenticated by its bearer service token and is not a browser CORS flow. Preview and local browser origins use separate non-production configuration and never a wildcard.

The current API reflects any browser origin and makes cookies secure only when `VERCEL=1`. Before Ubuntu traffic is enabled, implementation must:

- add `CORS_ALLOWED_ORIGINS` parsing with exact-origin matching;
- add `COOKIE_SECURE=true` so cookie security is independent of the hosting vendor;
- issue host-only `bp_session` and OAuth-state cookies with `HttpOnly`, `Secure`, and `SameSite=Lax` for the same-site `app` and `api` subdomains;
- retain explicit local-development behavior through non-production configuration;
- make `/auth/meta/dev-complete` unavailable whenever `NODE_ENV=production`; local use additionally requires an explicit opt-in such as `ENABLE_META_DEV_COMPLETION=true`, rather than inferring safety from the absence of `VERCEL`;
- replace the API and DM worker's `rejectUnauthorized: false` Supabase connection with CA-backed certificate and hostname verification. The production env contract supplies the downloaded Supabase CA through a mounted file and uses `verify-full` semantics;
- configure Fastify to trust only the single private Caddy hop and configure Caddy to overwrite forwarding headers, so rate limits and audit logs use the real client IP without trusting a browser-supplied `X-Forwarded-For` value;
- update Kakao and Meta callback origins to `https://api.danbammsg.co.kr` and post-login redirects to `https://app.danbammsg.co.kr`.

Secrets stay outside Git. Vercel stores client-safe build variables, while Ubuntu stores API and worker secrets in `/opt/brand-pilot/shared/env/` files readable only by the deployment account. Only variables prefixed for Vite exposure may enter the customer bundle, and no service credential may use that prefix.

Early real-domain testing is enforced by the API, not by hidden navigation or provider test mode alone. With `LAUNCH_ACCESS_MODE=restricted`, production startup requires non-empty explicit test identities; Kakao callback checks the returned provider subject before creating/loading a customer session, and authenticated Meta starts plus all customer routes require either an allowlisted application user or a user linked to an allowlisted Kakao subject. A denied identity receives no workspace, brand, session, upload URL, or job. Administrator and worker routes continue to use their separate service authentication. Switching to `public` is a recorded post-gate deployment change with a rollback, never an optional runtime default. Vercel Deployment Protection is not a substitute for these application controls. During the legacy snapshot only, Standard Protection is one layer of a stronger reversible barrier that also uses project pause plus a deny-all WAF rule, a zero-Function prebuilt static tombstone, single-audited-owner access, and complete Git/deploy/API automation shutdown; the marker is forbidden if any authenticated principal, runtime, or build can still reach a historical writer.

Restricted mode also covers signed Instagram webhooks and the existing DM queue. When webhook processing is enabled before public launch, production startup requires exact test Instagram recipient-account and sender IDs. After signature verification but before any customer/message persistence, job creation, or reply, the API accepts automation only when both IDs are allowlisted; other valid events are acknowledged without side effects and counted in a redacted denial metric so Meta does not retry them indefinitely. At the legacy fence watermark, every pending/in-flight DM reply job is resolved back to its recipient account and sender; non-allowlisted or unresolvable work is atomically quarantined before a new worker can claim it. While restricted, the server rechecks both IDs when granting a DM claim and the channel adapter rechecks them again immediately before sending, so a pre-fence job or race cannot bypass ingress filtering. Quarantine is not automatically released by switching to `public`: the operator separately cancels stale work or approves an age-bounded, idempotent requeue after reviewing user impact. Initial restricted tests use a separate Meta development/test app plus professional test account.

Before the live provider switch to Ubuntu, every controllable non-provider mutation surface is frozen and drained, timestamped provider/database/queue/storage watermarks prove zero unfinished non-test obligation, the separate storage-less cutover receiver is live, and `legacy_general_fence_committed` has completed all old-project storage/database/runtime revocation plus historical-deployment deletion. During the short switch, `LEGACY_CUTOVER_MODE=freeze` permits exactly two predeclared, one-time Ubuntu probes and no ordinary OAuth or mutation: one signed delivery bound to the exact test recipient, sender, and event ID, and one OAuth start/callback bound to the exact test application user/provider subject, browser session digest, workspace, brand, credential set/app, callback, nonce, and expiry. The callback consumes that transaction atomically; any different start, callback, delivery, or replay is denied. An unexpected signed non-test event receives a provider-tested retriable failure with no persistence and aborts before the second floor, so provider URLs return only to the already-smoked narrow receiver; the general Vercel application or storage authority never returns. If provider retry behavior cannot be proven, the switch is blocked for a dedicated continuity design. Ubuntu must pass those exact probes, drain deliveries still addressed to the temporary receiver, and reach the final pre-marker zero delta. Failure drains Ubuntu and restores/verifies the receiver. Success first durably records `provider_revocation_committed`, then revokes the receiver database role and deletes the secret-bearing temporary receiver project/deployments/domain. The shared live Meta app secret itself remains unchanged on Ubuntu; rotating it would require a separate coordinated provider rotation. Any partial failure after that marker keeps provider URLs on Ubuntu, retries unfinished role revocation/project deletion, and falls back only to a prevalidated live-env-compatible Ubuntu image/config with OAuth and DM automation disabled. A retry that still targets the old callback after the marker is recovered from provider event/log IDs by Ubuntu and explicitly completed or quarantined; the receiver is never reauthorized. After authority expiry, mandatory reconciliation requires a second zero delta before stable manifests. The later public transition changes only access/DM policy, not an untested credential set.

Implementation first proves that the current job schema can represent an audited quarantine state that no existing claim query recognizes and can preserve the resolved recipient/sender plus fence watermark. If it cannot, the same narrow storage/job compatibility migration described below adds those fields/statuses before the legacy fence; a process-local list or merely stopping one worker is not accepted as quarantine.

### OAuth transaction integrity

Every OAuth start creates a high-entropy transaction bound to the provider, active provider credential-set/issuer app when applicable, the initiating browser session and user when known, the active workspace and brand when the flow connects a channel, the exact registered callback, a fixed allowlisted post-login destination, and a short expiry. The callback reloads the current session, compares every applicable credential-set/user/workspace/brand binding, and atomically consumes the transaction before accepting the result; missing, mismatched, expired, reused, provider-set-changed, or provider-error callbacks fail closed. An arbitrary browser-supplied `returnTo` is never reflected into a redirect. Kakao pre-login transactions have null user/workspace/brand fields and may create/select them only after the verified code exchange; authenticated Meta transactions require all four tenant/session bindings plus the set that issued the authorization code.

Kakao uses PKCE with `S256`, keeping the verifier server-side and sending it only during the authorization-code exchange. Kakao's current OpenID metadata advertises `S256`, so this is a required production path rather than an optional enhancement. For Instagram Login and the Facebook Login trend flow, implementation verifies PKCE support against the exact current Meta endpoints and test applications. When an endpoint supports `S256`, it receives the same verifier/challenge treatment. When it does not, the code must not pretend that an ignored PKCE parameter is protection: it uses a durable server-side, single-use transaction record with session/user binding instead and records the provider limitation in the operator guide.

The existing repository has cookie state but no durable OAuth transaction store, and `user_sessions` stores only `user_id` while session lookup silently selects the oldest brand. The authentication migration adds nullable active `workspace_id`/`brand_id` columns with tenant-consistent foreign keys to `user_sessions`, makes authenticated session resolution use those exact values, and defines an authorized active-brand switch instead of an implicit query order. It also adds `oauth_transactions` containing only a state digest, provider, nullable credential-set ID/issuer app ID, encrypted verifier when applicable, session ID/digest, nullable `user_id`, `workspace_id`, and `brand_id`, redirect enum, `expires_at`, and `consumed_at`; indexed bounded maintenance removes abandoned rows. Foreign keys and tenant-consistency checks prevent a session or transaction from naming a brand outside its workspace.

The migration adds immutable `credential_set_id` and `issuer_app_id` provenance to each encrypted Instagram channel credential and each `instagram_trend_connections` credential. New callbacks write both from their bound transaction, never from a browser field. Existing active Instagram Login ciphertext is backfilled as the retained live set only after the pre-fence decrypt/provider identity audit proves it was issued for that live app; rows with unknown/mismatched provenance block cutover or become reconnect-required instead of being guessed. Existing trend credentials are not guessed or backfilled because they were issued by the former shared app: before the separate trend app is activated, one transaction atomically changes every connected row whose provenance is absent or differs from the new trend set/app to `needs_attention` with `last_error_code=issuer_app_changed`. A trend resolver accepts `connected` only when both immutable values exactly match the active trend environment, and only a newly bound OAuth callback may replace the credential and restore `connected`. Once active, provenance cannot change in place—reconnection creates/replaces the credential through a new bound OAuth result. Public launch requires zero active unknown/test Instagram rows and zero connected trend rows with unknown, old, or mismatched provenance. Maintenance selects and mutates Instagram rows only when their immutable set/app exactly matches its active environment; audit-only mode can inspect counts across Instagram sets but cannot refresh/rewrite them.

The same migration adds `worker_principals` with a unique fixed `worker_id`, worker kind, allowed job types, high-entropy token hash, active/expiry/revocation state, and audit timestamps. Raw tokens are shown once by an operator command and stored only in that worker's secret file. API authentication derives identity and allowed claim routes from the token record; a request body cannot choose or override them. Each Ubuntu container and retained PC has its own principal and can be revoked independently. It also adds one deploy-owner-only `deployment_cutover_state` row plus append-only transition events. A constrained function may advance only `prepared` → `legacy_general_fence_committed` → `provider_revocation_committed` → `retired`, binds the release/cutover manifest hash and timestamp/operator identity, and rejects rollback, skip, or overwrite; no application, worker, maintenance, receiver, or administrator role can read or mutate secrets through it. The database state, fsynced host copy, and signed off-host artifact must agree before each governed action. This focused security migration is required hardening rather than a consequence of Docker or the monorepo move and follows the normal rollback-compatibility process. Private-artifact sealing, DM-quarantine, deletion-outbox, or maintenance-state constraints may still require one additional narrow compatibility migration only if the implementation proofs described below fail.

### Non-publishing maintenance owner

The application scheduler and old Vercel Cron remain off, so a distinct `credential-maintenance` one-shot image is the sole first-public owner for three bounded duties: refresh/expiry health for active Instagram credentials; indexed batch deletion of expired/consumed `oauth_transactions`; and lease-based, idempotent draining of private-object deletion outbox plus abandoned-object retention. A host `brand-pilot-maintenance.timer` uses `OnBootSec=2m`, `OnUnitActiveSec=5m`, `RandomizedDelaySec=30s`, and `Persistent=true` to invoke the Compose one-shot service; its runtime limit is shorter than the interval. The process acquires one database advisory/lease lock, emits a last-success heartbeat/metrics, retries bounded batches, and alerts when no success occurs for 15 minutes or backlog/age thresholds are exceeded. API deletion responses expose pending/completed state and never claim the provider object is gone before the outbox item succeeds.

Before installing the timer, implementation proves that existing rows can durably represent deletion object/tenant/operation, idempotency key, attempt/next-attempt, state, lease token/expiry, last error, completion, maintenance owner, and last-success heartbeat and that no current worker query can misclaim them. If the proof fails, the same narrow compatibility migration adds only the missing outbox and maintenance-run/lock state. Process-local timers, an advisory lock without durable last-success/backlog state, or an unimplemented `storage_cleanup` enum value do not satisfy this contract.

This image is built from a dedicated entry package whose dependency/import graph cannot reach scheduler, prepare/publish, public-promotion, channel publishing adapter, or public Blob code. It has a narrow maintenance database role, the active Instagram credential set plus `CREDENTIAL_ENCRYPTION_KEY`, and the isolated private-storage credential; it has no API/admin/worker/publication token, public-bucket credential, model/Codex credential, or customer route. Database grants cover only OAuth transaction cleanup, channel credential health/refresh fields, maintenance locks/heartbeats, and private deletion/retention rows. Build/import tests and runtime negative tests prove it cannot read or mutate publish queue/attempt/artifact state or invoke Meta publishing. Its image digest, timer unit revision/schedule, stable instance ID, lock key, last-success threshold, and credential-set ID are part of the release manifest. Rollback stops the timer, waits/fences its lease, restores the matching image/env/unit, runs one dry-run plus real bounded cycle, and then re-enables it; an external alert fires if no healthy cycle occurs.

No schema migration is introduced by the repository move or split deployment itself. The required authentication/session/worker-principal/cutover-ledger migration and any artifact-sealing, DM-quarantine, deletion-outbox, or maintenance-state change proven necessary by compatibility tests are separate security migrations, not hidden Docker prerequisites. Before any production DDL/grant change, the operator must prove a current recoverable backup/PITR or encrypted logical-export point by restoring it into an isolated scratch database, record the recovery owner and pre-migration schema/version fingerprint, and verify rollback/forward-reader compatibility; failure stops before migration. Supabase database backups cover database state, not the bytes stored through Storage, so they never substitute for the independent object manifests, survival rehearsal, evacuation snapshot, and restore checks in this design. A database-authorization operation is required regardless of those schema decisions: the migration/owner credential is deploy-only; the API receives a non-owner runtime role with only its enumerated tables, sequences, and functions; DM/Wiki receives a narrower role limited to its queue, Wiki, heartbeat, and lease operations; maintenance receives a disjoint role limited to OAuth cleanup, credential health/refresh, maintenance locks/heartbeats, and private deletion/retention state; and the temporary Vercel cutover receiver receives a separately revocable role limited to account lookup, signed-event dedupe/insert, and queue handoff. The receiver role cannot start/complete ordinary OAuth, mutate credentials, access objects, or claim/send work, and is revoked only after `provider_revocation_committed`. No runtime role may create/alter schema, manage roles, inherit the migration owner, or reach unrelated data; maintenance additionally has no publish queue/attempt/artifact grants. Positive tests prove required operations work, while negative tests prove DDL and unrelated or publication data remain inaccessible. The backup evidence ID, migration floor, chosen compatibility-schema version, and forward/rollback reader matrix are part of the release manifest.

### Legacy Vercel API write fence and retirement

The existing `api-three-omega-89.vercel.app` project and its immutable deployment URLs may still hold database, Blob, provider, worker, administrator, cron, model, and credential-encryption values. Removing an alias or changing the customer UI is not a security boundary because an old deployment URL can still be called. The legacy source-store registry includes at minimum the Vercel Blob namespace and the main Supabase project's public `brand-assets` bucket, plus any additional backend/bucket discovered in code, environment inventory, or stored URLs. Before rotating any application storage token, the operator inventories every legacy alias/deployment, callback, Cron, credential consumer, and source store. The Vercel Blob inventory includes store ID/owner/team, authentication mode (`static-token` and/or `OIDC`), every connected project, and the connection revision; a project connection is authority even when no long-lived token is present. Without printing secret values, a fingerprint/role inventory maps every legacy database and storage credential/connection to every consumer, including immutable Vercel deployments, old DM/Wiki processes, and retained generation/analysis workers. Every non-Vercel consumer that shares legacy authority is first moved to its new narrow database role and/or per-worker private job capability, or fully stopped; new claims/uploads are fenced, exact in-flight leases/uploads drain, and negative probes prove that consumer cannot write the legacy database/queue/store. Only a credential independently proven to be Vercel-exclusive may skip a consumer cutover.

Before any irreversible fence, the operator creates a separate Vercel project and attaches temporary `cutover-api.danbammsg.co.kr`. Its initial environment and integration inventory must be empty: it is never connected to the old Blob store, receives no Vercel Blob OIDC binding, and receives only the temporary narrow receiver database value plus the audited live Meta receiver secret/verify token. The project deploys and live-smokes one source-revision/deployment-ID-pinned `legacy-cutover-receiver`. Its route graph contains only health, webhook verification/signed delivery, a legacy Instagram callback that can only reject/drain already-expired transactions without exchanging or storing a token, and a secret-free maintenance response; it has no login start, customer/admin/upload/job/Cron/worker/publication route. Its database role is limited to account lookup, idempotent signed-event insert/dedupe, and queue handoff, and it has no Blob/Supabase Storage, broad database, worker/admin/cron/model, public-publisher, or `CREDENTIAL_ENCRYPTION_KEY` authority. A route/import/grant plus invoked-runtime environment test proves this boundary. Every outstanding old OAuth transaction is consumed/expired before this receiver becomes the rollback target, so rollback does not depend on starting or completing a new OAuth flow there.

The operator then builds a reversible old-project reachability barrier while the cutover ledger is still `prepared`. It first captures an encrypted off-host recovery copy and non-secret fingerprints of the old project's environment definitions, Blob/OIDC bindings, deployment inventory, Cron configuration, Git connection/auto-deploy policy, deploy hooks, API/CLI/integration tokens and principals, in-flight builds, team/project members, access groups, pending invites, protection/WAF/bypass/share-link settings, and aliases. All deploy-capable members/access groups/service principals are removed, downgraded, or session-frozen so exactly one MFA-protected audited cutover owner and one short-lived operation token remain; that owner is an explicit trusted control-plane principal, not evidence that Vercel has technically disabled Owner deployment rights. If team-level roles leave any additional deploy principal, the barrier fails. Git/auto-deploy is disconnected, deployment-only hook/API/CLI/integration credentials are fingerprinted and deleted or revoked, their downstream caller mappings and least-privilege replacement plan are sealed in the abort manifest, Cron is disabled, and all in-flight builds/deployments/functions are drained to zero with a stable deployment-list watermark. The operator removes every broad/static secret from old-project environment settings. Using a provider-supported reconnect procedure rehearsed against a disposable project, the operator then reversibly detaches the old project from every Blob store/OIDC binding, records the exact store/project/team/connection revision and abort reattachment procedure, waits the documented or measured maximum lifetime of every previously issued store token plus margin, and proves that a fresh owner-created no-op build and runtime receive no old-store claim or broad database/storage value. If exact reattachment plus read/write smoke cannot be proven before detachment, the transaction stops. Finally, the operator uploads a reviewed prebuilt static tombstone with zero Functions, build command, install hook, runtime route, or OIDC-consuming code; no project build executes to create it. Existing immutable deployments retain their already-built environment snapshot and remain only a tested pre-marker rollback artifact behind the independent runtime barrier.

After the live Instagram registrations move to the isolated receiver and the old production domain is assigned to the static tombstone, the old project enables current Standard Protection, removes every bypass/exception/share link, applies a project-wide deny-all WAF rule, and is paused through the platform control. An exhaustive generated/branch/commit/production-URL matrix must deny requests from unauthenticated clients and from the remaining authenticated owner; a named sacrificial historical mutation route must fail without application execution. Negative automation probes prove removed Git, hook, API/CLI, integration, and redeploy callers can no longer create deployments. Because Vercel Owner remains deployment-capable, the gate does not claim that no build can technically start: the sealed no-op owner build proves instead that current environment stripping plus the expired, detached Blob/OIDC connection gives every new build/runtime zero old database/storage authority, and any other owner action or deployment-list change invalidates the snapshot window. Historical runtimes are covered separately by the all-URL WAF/protection/pause matrix and reversible database write fence. Audit/build/function logs must remain unchanged for the full snapshot window. If the current plan, team access model, store-detachment/expiry proof, WAF scope, or project URL behavior cannot prove this no-writer barrier for every historical runtime and every non-owner deployment principal, the transaction stops in `prepared`; quiet scans or an unspecified journal are not an alternative.

The same reversible pre-marker barrier covers the database. After every other legacy database consumer is moved or stopped, deploy-owner tooling fingerprints the old grants, revokes write privileges from the legacy broad role where they are independently reversible, terminates its sessions, and proves denied create/update/delete while the receiver's disjoint append-only handoff role still works. Any path using a service credential that cannot be reversibly write-fenced blocks the cutover. A row before-image, CDC interval, WAL/PITR point, or restore test remains mandatory recovery evidence where applicable, but none substitutes for the continuously proven zero-writer barrier required before the first marker.

A full abort is available only while every ledger copy remains `prepared` and follows one idempotent, manifest-bound reverse procedure; an ad hoc alias or grant change is not an abort. The prepared barrier may permanently revoke fingerprinted deployment-only hook URLs, API tokens, sessions, or invitations, but it has not yet revoked the old application's data/storage/database runtime authority. The manifest therefore binds each closed control, its old caller/configuration fingerprint, its approved least-privilege replacement class, and every downstream caller that must switch. Abort restores the recorded semantic configuration with newly issued hooks/tokens/invitations where an old secret cannot be resurrected, atomically updates and smokes every inventoried caller, records the new fingerprints, and never re-enables a revoked credential. With both sides still frozen, it restores the old-project environment definitions and the exact recorded Blob/OIDC store connection through the rehearsed reattachment procedure, waits for successful old-runtime read/write smoke, restores exact database grants, production alias, project pause/WAF/protection/bypass/exception/share-link policy, Cron, Git/auto-deploy, deploy hooks/integrations, permitted member/access-group/API-principal set, and automation behavior to their recorded contract; moves the exact Instagram redirect/webhook registrations back from the temporary receiver to the audited old production URL; then live-smokes signed delivery, login rejection/allowed behavior, database/object writes, build ownership, and scheduled-entry ownership on the old deployment. It reconciles/deduplicates every receiver and old-target event cursor before draining the receiver, removes every temporary provider registration, and revokes the receiver database role. The receiver could not be deny-all while it was the live callback, so the abort now explicitly removes every bypass/share link, applies a project-wide deny-all WAF rule, and proves both unauthenticated and authenticated requests are denied without Function execution. Only after that WAF proof, while the receiver project/domain binding remains owned, does it remove the authoritative `cutover-api` DNS record and wait the recorded DNS TTL plus safety margin until authoritative, multiple recursive resolvers, and off-network probes show no record; only then does it remove the Vercel domain binding and delete all receiver deployments/project, followed by no-binding/certificate/HTTP probes. Each reverse step is restartable and records completion; a partial abort stays frozen in `prepared`, keeps exactly one declared provider target, retains project ownership until DNS convergence, and retries without declaring either abort or first-floor success. Failure to apply or prove receiver deny-all leaves DNS and ownership intact. No part of this restoration is allowed after `legacy_general_fence_committed`.

Only after both barriers are continuously proven does the operator capture the recoverable cutover snapshot. A provider-capability matrix records the native scope and revocation boundary of every store before any credential is issued. Where the provider truly supports it, separate operator-only evidence list/read and independently revocable exact-namespace recovery credentials are used and never enter an application runtime. Vercel Blob is treated differently under its current native contract: project OIDC and `BLOB_READ_WRITE_TOKEN` are store-wide read/write authority, and `list()` does not become read-only merely because the migration command promises not to write. The runbook must never label that authority read-only or namespace-scoped. Instead, one isolated migration controller authorization is kept outside every application, protected by two-operator approval, a signed manifest/command allowlist, immutable audit output, and code with no delete command. Evidence mode permits only source-side list/head/get; it writes downloaded bytes only through a separate independent-destination credential/endpoint and forbids source-side copy/put/delete, while recovery mode permits only manifest-listed exact-key put/conditional-overwrite or signed per-object operations. The controller's underlying store-wide authority, source and destination credential fingerprints, operator approvals, start/end time, every issued object operation, source before/after count/hash proof, and detach/revoke proof are explicit evidence. Delete is allowed only in a separately approved cleanup run after preservation. Because that compensation is not cryptographic least privilege, Vercel Blob is assigned to the complete-evacuation preservation branch unless a future current-provider capability review proves independently revocable scoped credentials and the full survival gate; if the controller boundary or audit cannot be proven, the first marker is blocked. Before the real snapshot, sacrificial objects prove byte/checksum/metadata-preserving restore and stable URL/reference behavior. The snapshot downloads every source byte plus required metadata and writes it through the independent destination, then performs two full source listings/checksum passes with identical count/byte/hash results and zero source mutation while protection logs remain quiet. Database evidence uses one consistent transaction snapshot tied to an exact WAL/LSN or export point, the zero-writer proof, and a receiver event cursor so the receiver's allowed append-only deliveries are reconciled separately. If a backend cannot reproduce an exact object/URL, the independent copy becomes the recovery source and deploy-owner tooling must be able to atomically switch every affected database/application reference and pass dual-read rollback before the first marker. A mismatch, unexplained write, missing before-image, failed restore, or changing fixed-point result returns to `prepared` and forbids the first marker.

The deployment tool maintains a monotonic two-floor cutover ledger in the deploy-owner-only database row/append-only events, fsynced `/opt/brand-pilot/state/`, and a signed off-host release artifact. All three copies bind the same manifest hash and must agree before a governed action. The constrained database transition is the atomic source step; host and off-host copies are then written and verified synchronously. A crash or network failure between copies performs no revoke/delete and resumes only by propagating the already-committed database state forward—never by rolling it back. ## Customer-Controlled Model Worker Security Boundary

Instagram messages, Wiki sources, uploaded documents, crawled pages, brand context, and generation briefs are untrusted input. They must never be placed into a general-purpose agent process that can inspect the filesystem, environment, network, or shell. The current DM/Wiki Codex child inherits database, worker, and model credentials. The retained card-news, blog, and marketing children inherit worker/Blob tokens while enabling shell access and `danger-full-access`; brand-intelligence and subject-analysis children filter some variables but still pass model/Codex/home credentials with a readable filesystem. Moving those processes to another PC does not remove prompt-injection or credential-exfiltration risk, so none of these current paths is a public-production configuration.

The production default for DM/Wiki, brand intelligence, subject analysis, card news, blog, and marketing is a direct, tool-less model API call from the parent worker. It uses no shell command, MCP/tool definitions, browser, arbitrary URL retrieval, or mounted Codex login directory. The model receives only minimum tenant-scoped data, never environment variables or credentials, and returns a strict versioned JSON schema with bounded fields. The application validates and sanitizes the parsed object, discards unknown fields, limits links and output length, and maps it to an allowed reply, analysis, render specification, or manual-handoff action. Invalid, timed-out, over-budget, or policy-rejected output fails safely rather than becoming a command or raw published text.

Private draft upload and worker completion remain ordinary parent-process operations after model output validation. The model call/child never receives `WORKER_API_TOKEN`, a job capability, `BLOB_READ_WRITE_TOKEN`, DB/admin/provider credentials, `CODEX_HOME`, or a user home directory. A generated asset specification may name only fixed roles and a job-scoped output path; the parent validates path, size, MIME, and manifest before using its object-specific job upload capability. Only the API/publisher owns the public-bucket credential used later at approved publication. The model key remains in the parent solely for the provider HTTPS client, and any future helper process receives an explicit minimal environment and destination-limited network policy.

A dedicated image-generation child is the only pre-approved exception to the no-tool rule. It may expose exactly the reviewed image-generation tool, a disposable job directory, and required Codex authentication, but no shell, general filesystem/browser/network tool, worker token, or Blob token. Its parent validates images and uploads them. Threads/reel/image paths that currently disable shell still receive explicit child-environment, output-directory, and canary tests before launch; shell absence alone is not assumed to prove the boundary.

Logs contain request IDs, model/version, latency, token usage, and outcome but no full customer input, prompt, response, key, home path, or canary value. Project-level spending limits, per-job token caps, rate limits, and alerts acknowledge that the default text/analysis paths are billed API usage rather than Codex CLI subscription usage.

Release evaluation runs per worker and includes Korean and English prompt injection, instructions to reveal system prompts, `printenv`/`.env`/filesystem/network requests, cross-tenant retrieval attempts, malicious URLs, oversized content, malformed structured output, unsafe render paths, and a synthetic secret canary that must never appear in a reply, asset, manifest, or log. Fixed safe-response/specification cases detect behavior regressions. Keeping any other Codex CLI path requires a separate approved design with a dedicated OS identity/container, isolated credentials, destination-limited egress, disposable filesystem, explicit child environment, disabled shell/general tools, and equivalent adversarial evidence; it is not a configuration switch in this release.

## Private Workspace Asset Boundary

Customer-uploaded PDF, XLSX, and images can contain confidential or personal information. Generated card/news/blog/marketing drafts, analysis archives, extracted text, intermediate images, and other derivatives can reveal the same information before approval. All of them are private by default in a private Supabase Storage bucket, or an equivalently reviewed private provider bucket. Only assets already published or explicitly approved for immediate publication live in the separate public bucket.

The later public-launch security release uses a distinct Supabase project as a storage-only security boundary because Supabase service-role and generated S3 server keys bypass RLS across a project. The private-storage project contains no application tables, no public bucket, and no unrelated application data; the main application database project exposes no service-role/secret key to the API. Startup compares project references, requires an inventory containing only the declared private bucket, and rejects accidental reuse. Release tests prove the private key is rejected by the main Data API and publication backend, the main project's keys are absent, and the application surface cannot select, list, create, or mutate another bucket. Moving later to a provider credential with enforceable bucket/prefix IAM is compatible, but a full-project key in the main application project is never an acceptable fallback.

For browser uploads, the authenticated API authorizes workspace and brand membership, allocates an unguessable tenant-scoped object key, and issues either a short-lived single-object upload URL or accepts a bounded streaming API upload. Confirmation performs a provider metadata lookup and verifies object key, byte size, checksum, declared MIME type, detected file type, and ownership before the row becomes usable. The authoritative database value is the private object key/path; short-lived signed URLs are never persisted.

Each worker principal token authenticates claim/heartbeat/report operations as one server-fixed worker ID/kind and allowed job-type set; client input cannot select a different identity or claim route. A successful allowed claim returns a short-lived signed or opaque job capability bound to that principal, job ID/type, workspace, brand, lease token/expiry, and the exact allowed input/output object IDs and operations. The API reloads the active lease and checks every binding before streaming an object through an authenticated bounded proxy or issuing a single-object signed read/upload URL. A renewed or reassigned lease immediately invalidates the old capability and prevents new access grants.

Because a provider-signed URL may remain usable until its own expiry, its TTL is `min(short configured cap, remaining lease)`. Every output key includes the lease nonce, is immutable, and rejects overwrite. Worker completion reloads the current principal/job/lease, requires the exact registered object ID/key, verifies checksum/size/MIME, and atomically seals an accepted-artifact record containing the immutable object identity, metadata, job, tenant, lease nonce, and completion time before ending the lease. A stale upload can therefore reach only an orphaned key that is quarantined and later cleaned. Operations needing immediate revocation use the opaque streaming/one-use API path rather than a provider URL. Workers cannot list buckets, choose another tenant/path, or use the capability after completion, failure, cancellation, or lease expiry. The capability stays in the ordinary parent process and is never sent to a model child.

Implementation first proves whether an existing artifact row can carry that sealed identity with uniqueness, immutability, and tenant/job constraints. If it can, no extra table is added; if it cannot, the private-storage narrow migration adds only the accepted-artifact fields/table and constraints needed for this contract. The proof and chosen schema version are recorded before migration tooling is allowed to copy objects.

Generation workers upload validated output to a lease-nonce-scoped immutable private draft path. Approval and publishing normally occur after the worker lease has ended, so public promotion does not require a fictitious active lease. Instead, at the actual publish transition the API/publisher requires the approved/publishing state and the sealed accepted-artifact ID, re-reads that exact immutable key, re-verifies its recorded checksum/size/MIME and tenant ownership, records the public artifact mapping, and only then copies the required asset into the public publication bucket and gives the channel adapter the public URL. Any mismatch blocks publication; rejected, merely previewed, scheduled-but-not-yet-publishing, unsealed, stale-lease, and analysis-only assets remain private and are viewed through authorized short-lived URLs. Deletion uses an idempotent outbox/retry path, and retention cleans abandoned objects without deleting evidence or drafts still referenced by an active job, review, or audit requirement.

Existing compatibility fields such as `storage_url` may temporarily contain an authenticated API reference, but never a permanent signed URL. Implementation first proves that every reader can resolve the existing `storage_path`; only if a current non-null/check constraint prevents this contract is a narrow forward-compatible migration added.

Conversion is explicitly expand/migrate/contract: deploy a compatibility release that dual-reads legacy public and new private references while writing every new non-public object privately; cut over or fence every shared legacy database/storage consumer; freeze/drain every controllable ordinary ingress; and live-smoke the isolated storage-less cutover receiver. While state remains `prepared`, move the provider to that receiver, protect every old generated URL, route the old production domain only to a secret-free tombstone, reversibly write-fence the broad database role, and prove zero reachable old writer. Capture two identical full object/checksum passes plus an independent byte/metadata copy and one WAL/LSN-bound consistent database snapshot; prove exact-key recovery with the sealed operator-only recovery credential or the independent-store atomic reference-switch fallback. Only then record `legacy_general_fence_committed`, revoke runtime object mutation before broad database/runtime authority, restore/reconcile any destructive delta, remove store bindings, and delete every historical deployment except the tombstone. Next switch and smoke the live provider on Ubuntu, drain old receiver deliveries, and reach final pre-marker zero. Success records `provider_revocation_committed` before receiver database-role revocation and isolated secret-bearing project deletion; the shared live Meta secret stays on Ubuntu. After DB authority expiry/project deletion, reconcile every remaining provider/database/queue/object delta into explicit Ubuntu completion or quarantine and prove the second zero delta. Only then may the operator seal the stable per-backend manifests containing backend/bucket ID, provider object ID/path, size, creation time, and a downloaded checksum when the provider does not expose one. Join the union of stable manifests to every database reference plus publication state.

Deleting the secret-bearing old project requires one complete preservation branch, recorded per store. In the survival branch, independent full-namespace list/read/delete control and store lifecycle independence are proven by provider ownership/binding evidence: connect a disposable Vercel project to the same production store with the same binding mode, delete that project, and repeat bounded namespace/object operations through the independent credential. Object classification and migration may then continue against that surviving store after old-project deletion. In the evacuation branch, before project deletion the stable manifest is used to checksum-copy every preservation-required object: attested publications to the independent public backend, referenced non-public objects to private storage, unreferenced/orphan/mock/unverifiable objects to private quarantine/evidence, and every still-ambiguous raw object plus metadata to a complete private evidence snapshot. Every resolvable database/application reference is switched, retained compatibility code passes dual-read and rollback smoke, and a query proves zero remaining resolvable project-bound reference plus zero count/byte/checksum omission before deletion. An ambiguous item need not be prematurely classified to preserve it, but the entire source evidence must already be independent of the project. Only after the selected branch succeeds may the project and deployments be deleted and re-probed.

Before any `published` classification, audit every historical `published`/`succeeded` row and every external ID/URL: a database status, synthetic/mock ID, or URL alone is not evidence. `published` requires a provider-side lookup or separately verified durable publication attestation that binds the real provider media ID/permalink, expected channel/account, source artifact, and successful adapter result. Missing, mismatched, deleted, or unverifiable evidence fails closed as non-public. Every object in every store is classified separately as `published`, `referenced-nonpublic`, `unreferenced`, or `ambiguous`; public launch and the storage floor require both per-store and combined zero unclassified and zero unresolved ambiguous counts. Manual review must resolve each ambiguous object to one of the other three states with recorded evidence. Referenced non-public objects are copied privately, verified by count/size/checksum, and switched in batches with a rollback map. An unreferenced object—including an upload that succeeded before its confirm call failed or the browser closed—and every historical mock/unverifiable publication are copied into a private quarantine/evidence prefix with their manifest/audit records and then have their public originals removed after verification. An ambiguous object resolved as non-public follows the same private-copy, public-delete, and denial path; only provider-attested genuinely published assets remain public. For every deletion in each backend, the migration records the old public URL, waits for that provider/CDN's invalidation, and then proves from an unauthenticated off-network client that the old URL no longer returns the object; denial before deletion is not accepted as evidence. After the bounded rollback window the same delete-then-probe order applies to remaining referenced non-public originals, followed by revocation of every operator migration credential. The rollback floor advances only after retained rollback code can read private references, all ambiguous items are resolved, and all per-backend post-delete denial probes pass; a legacy write token is never returned to application code.

Locally ignored `.env` files are not copied into the monorepo or Ubuntu host. A credential is rotated when its value was printed, committed, shared, or otherwise exposed; merely existing in a Git-ignored local `.env` is not exposure. The OpenAI key confirmed in tool output during this review is rotated. `CREDENTIAL_ENCRYPTION_KEY`, session secrets, provider secrets, database credentials, and other values are preserved unless an exposure audit identifies them, because uncoordinated rotation can invalidate sessions or make retained encrypted credentials unreadable. New Ubuntu secrets are provisioned through mode-`0600` server files and never copied wholesale from a developer `.env`.

## Independent Scheduler and Publication Gate

The current scheduler always calls the due-publication path, and the current `INSTAGRAM_PUBLISH_ENABLED=false` branch can still synthesize an external ID/URL and mark the attempt and queue item succeeded/published. Publication is also reachable without the scheduler through customer/admin output-publish, queue schedule, direct-publish, retry, and internal `publish-due` Cron routes. Therefore one central fail-closed publication gate runs after caller authentication/authorization but before `prepare`, schedule/queue insertion, claim, private-to-public promotion, attempt/status/external-ID mutation, or provider call at every route and repository entry. Disabled requests return the stable `publication_disabled` response and no success-shaped mock data; the UI shows the feature as unavailable. Defense-in-depth checks inside `prepareAiContentPublish`, `publishQueueItem`, and `runDuePublishing` prevent an omitted route guard from mutating state. Production defines only two valid states: `PUBLICATION_PHASE=disabled` with both flags false, then the independently approved release floor with `PUBLICATION_PHASE=enabled` and both flags true. Both XOR combinations and an enabled phase without its recorded floor fail startup. The first public customer launch uses the disabled triple, even if other scheduled conveniences remain unavailable.

Publication is a later, separately approved release. Before it, implementation inventories all due/in-flight rows and classifies test versus real work; proves only a sealed, approved artifact at its actual publish transition can be promoted; verifies the live Meta adapter with a designated test account; exercises every disabled customer/admin/Cron entry and the underlying repository functions while both flags are false and proves byte-for-byte relevant database state plus storage/channel state is unchanged; then runs one designated due row with both flags true and proves exactly one provider call, public promotion, external ID, and idempotent success. Exactly one scheduler identity and database lease/lock is allowed. Provider failure, timeout, duplicate invocation, SIGTERM, or rollback cannot mark success without the verified external result.

Activation deploys a new release manifest/environment revision that changes the publication phase and both flags together to enabled/true/true and records the release floor, scheduler identity, due-row watermark, publishing-adapter version, and rollback disposition. Rollback disables new claims first, drains/fences the current lease, and restores the disabled/false/false triple before code rollback. If non-publishing scheduled tasks are needed earlier, they use only the isolated maintenance owner above or require another task-level process that provably cannot import or invoke publication; the application scheduler is not used as an implicit fallback.

## Performance Constraints

- The customer entry JavaScript must be split by route and remain below a documented budget established from the first split build.
- Static assets use immutable caching while `index.html` remains revalidated so new releases do not strand users on stale chunk names.
- The customer build installs from the committed Brand Pilot npm lockfile.
- Ubuntu runs prebuilt images and never installs npm dependencies during deployment.
- API, worker, and maintenance images use multi-stage builds and exclude UI, tests, documentation prototypes, caches, and local output; the maintenance build additionally excludes publication code and credentials.
- OAuth hardening adds bounded transaction reads/writes and cleanup; their indexes and expiry behavior are measured before launch.
- Private-asset conversion performs a one-time verified copy under a bounded dual-read window and changes worker/browser reads to short-lived object-specific access. It must not proxy large files through API memory without streaming and explicit size/time limits; publish promotion copies only required assets and is measured separately.

- The API already has Fastify injection tests and explicit cookie assertions that can be extended rather than replaced.

- The current API still reflects arbitrary CORS origins, ties secure cookies to `VERCEL=1`, and shares one Meta app credential pair across two incompatible login modes. These are known pre-cutover changes, not acceptable production defaults.

Public-launch security and private-storage work are tracked separately and do not expand these lanes.

The production deployment script gets an inline ASCII comment for its deploy/health/rollback sequence. Application components do not need architecture diagrams in code because their state flow is already expressed by focused modules and tests.

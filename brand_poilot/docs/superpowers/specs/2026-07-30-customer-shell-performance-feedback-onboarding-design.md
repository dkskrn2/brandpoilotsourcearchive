# 고객 셸·성과개선·문의·온보딩 상태 개선 설계

## 목적

기존 D안의 데이터와 기능을 유지하면서 다음 사용자 경험을 한 번에 정리한다.

- 성과·개선 화면의 정보 위계와 가독성을 개선한다.
- 중복된 데스크톱 헤더를 제거하고 사용량과 계정 기능을 사이드바에 통합한다.
- 고객센터 메뉴를 숨기고 피드백 팝업에서 문의를 접수한다.
- 문의 내역을 브랜드센터에서 확인한다.
- 최초 온보딩과 재분석 상태를 브랜드센터와 온보딩 화면에서 일관되게 연결한다.
- 여러 탭이나 브라우저에서 브랜드 분석이 중복 생성되지 않게 한다.

## 범위와 보존 원칙

### 유지

- 기존 성과 API, 최근 30일 집계, 관측·해석·실험 생성 기능
- 브랜드센터의 브랜드 코어, FAQ, 이용 방법, 가이드, 제품·서비스, 스타일 기능
- 확정된 브랜드 정보와 기존 문의 데이터
- 모바일 메뉴의 포커스 트랩, Escape 닫기, 본문 스크롤 잠금
- 데스크톱 사이드바 접기 상태 저장
- 기존 `/support` 직접 주소의 호환

### 이번 범위에서 추가하지 않음

- 성과 기간 선택, 신규 지표, 신규 채널 필터
- 사용자 아바타나 별도 계정 설정 화면
- 온보딩 과정에서 Wiki 생성
- 운영 환경변수 또는 비밀정보 변경

## 1. 성과·개선 화면

현재 API와 view model을 유지하고 화면만 재구성한다.

1. 상단에는 최근 30일 요약 지표와 데이터 상태를 배치한다.
2. 관측 결과와 해석을 한 영역에서 구분해 읽을 수 있게 한다.
3. 24시간·72시간·7일 측정 구간은 보조 정보로 축소한다.
4. 성과 콘텐츠는 비교 가능한 카드 또는 행 목록으로 표시한다.
5. 다음 실험과 `AI 구성안 만들기` 기능은 유지한다.
6. 콘텐츠 상세 팝업은 기존 접근성·재시도·원본 링크 기능을 보존한다.

백엔드 DTO와 집계 쿼리는 변경하지 않는다.

## 2. 공통 헤더와 사이드바

### 데스크톱

- 전역 상단 헤더를 제거한다.
- 각 화면의 자체 제목 영역은 유지한다.
- 생성 잔여 횟수와 다운로드 잔여 횟수는 사이드바에 표시한다.
- `준비 완료`, 회사명, 상단 계정 메뉴는 제거한다.

### 모바일

- 전체 헤더 대신 메뉴 버튼만 제공하는 최소 상단 바를 유지한다.
- 981~1080px 구간에서 사이드바와 모바일 메뉴 버튼이 모두 사라지는 기존 breakpoint 불일치를 함께 수정한다.

### 사이드바

- 세로 공간이 부족하면 사이드바 내부를 스크롤할 수 있게 한다.
- 데스크톱 접기와 모바일 메뉴 동작은 유지한다.
- 고객센터 메뉴는 숨기되 `/support` 라우트는 기존 링크 호환을 위해 유지한다.
- 오래된 브랜드 분석 링크를 `/onboarding/brand-intelligence`로 교체한다.

### 프로필 드롭다운

- 브랜드 프로필 영역은 직접 링크 대신 메뉴 버튼이 된다.
- 메뉴 항목은 `브랜드센터`, `로그아웃` 두 개다.
- 바깥 클릭, Escape, 메뉴 이동, 라우트 이동 시 닫힌다.
- 키보드 포커스 복원과 모바일 메뉴 닫기를 보존한다.
- 온보딩 미완료 사용자에게도 로그아웃 경로가 필요하므로 프로필 영역을 표시한다.

## 3. 피드백과 문의 내역

### 입력

피드백 팝업의 `의견 보내기`는 다음 두 값만 받는다.

- 문의 유형: 오류, 기능 요청, 채널, 계정, 기타
- 내용

제목, 전화번호, 이메일은 받지 않는다. 통화 예약 카드는 설정된 예약 URL이 있을 때만 표시한다. 설정이 없을 때 기존 고객센터 폼으로 보내는 fallback 링크는 제거한다.

### 저장 모델

기존 `support_requests`를 문의의 단일 저장소로 사용한다.

- 기존 문의와 운영자 답변 기능을 보존한다.
- `title`, `contact_phone`, `contact_email`은 신규 간소화 문의에서 선택값이 될 수 있게 스키마와 계약을 확장한다.
- 새 문의의 표시 제목은 문의 유형으로부터 서버가 생성한다.
- 기존 행과 기존 필수값은 수정하거나 삭제하지 않는다.
- 피드백 전용 `feedback_submissions`의 기존 데이터는 보존하되 신규 고객 문의는 `support_requests`에 저장한다.

### 표시

- 브랜드센터의 모든 탭 아래 공통 `문의 내역` 영역을 둔다.
- 접수일, 유형, 상태, 내용, 운영자 답변을 표시한다.
- 새 문의 접수 후 목록을 갱신한다.
- 고객센터 메뉴를 숨겨도 직접 `/support`로 접근한 기존 사용자는 기존 화면을 계속 사용할 수 있다.

## 4. 온보딩 상태 모델

사용자에게 노출되는 상태는 다음과 같다.

| 상태 | 최초 온보딩 브랜드센터 | 온보딩 화면 |
|---|---|---|
| `not_started` | 탭 숨김, `온보딩 하기` | Step 1 |
| `in_progress` | 탭 숨김, `분석중입니다` | 분석 로더 |
| `review_ready` | 탭 숨김, 완료 문구와 `분석확인하기` | Step 2 편집 |
| `confirmed` | 기존 탭 표시 | 완료 상태 |
| `failed` | 실패 안내와 다시 시작 버튼 | 오류와 다시 시작 |

`review_ready`가 사용자에게 보이는 “분석 완료”다. `confirmed`는 사용자가 Step 2 내용을 확인하고 완료한 뒤의 상태다.

### 재분석

이미 확정된 브랜드 정보가 있는 사용자가 재분석할 때는 기존 브랜드센터 탭을 유지한다. 상단 상태 안내로 `재분석 중입니다` 또는 `재분석 결과를 확인하세요`를 표시한다. 새 분석을 확인하기 전까지 기존 확정 정보가 계속 운영 기준이다.

## 5. 중복 분석 방지와 재진입

### 서버

- 기존 “확정된 현재 분석” 조회 의미는 유지한다.
- 별도로 브랜드의 최신 open workflow를 조회할 수 있게 한다.
- open 상태는 `queued`, `extracting`, `analyzing`, `review_ready`다.
- 분석 생성 시 브랜드 행을 잠근 뒤 기존 open workflow가 있으면 새 작업을 만들지 않고 기존 작업을 반환한다.
- DB partial unique index로 브랜드당 open workflow 한 건을 보장한다.
- 과거에 open workflow가 여러 건이면 가장 최신 한 건을 남기고 나머지는 삭제하지 않은 채 `failed/superseded`로 종료한 후 인덱스를 추가한다.

### 클라이언트

- 온보딩 진입 시 localStorage보다 서버 workflow 상태를 우선한다.
- 진행 중 workflow가 있으면 Step 1을 렌더하지 않고 분석 로더로 이동한다.
- `review_ready`면 해당 분석 ID로 Step 2를 연다.
- Step 1에서 분석을 시작한 뒤에는 Step 1 단계 버튼을 비활성화한다.
- 외부에서 Step 1 주소로 다시 진입해도 서버 상태에 맞는 단계로 이동한다.
- 실패 상태에서만 사용자가 새 분석을 시작할 수 있다.

## 6. 데이터 흐름

### 앱 셸

`AI 사용량 조회 → 사이드바 사용량 표시`

`브랜드 상태 조회 → 메뉴 잠금·배지·브랜드 프로필 표시`

### 문의

`피드백 팝업 → 유형·내용 검증 → support_requests 생성 → 브랜드센터 문의내역 갱신`

### 온보딩

`온보딩/브랜드센터 진입 → confirmed 분석 + open workflow 조회 → 화면 상태 결정`

`분석 시작 → 서버에서 기존 open workflow 확인 → 기존 작업 반환 또는 새 작업 생성`

`review_ready → 사용자 편집·저장·확정 → 기존 open workflow 종료 및 confirmed 활성화`

## 7. 오류 처리

- 사용량 조회 실패는 사이드바 전체를 막지 않고 사용량만 숨긴다.
- 문의 제출 실패 시 입력 내용을 보존하고 다시 시도할 수 있게 한다.
- 문의내역 조회 실패는 브랜드센터의 다른 탭 기능을 막지 않는다.
- 분석 polling 실패나 시간 초과 시 진행 포인터를 임의로 삭제하지 않고 서버 상태를 다시 조회할 수 있게 한다.
- 브랜드센터의 기존 확정 데이터는 재분석 실패와 무관하게 유지한다.

## 8. 구현 분할

충돌을 줄이기 위해 다음 네 영역을 독립 구현한 뒤 통합한다.

1. 성과·개선 UI
2. 공통 셸·사이드바·프로필 메뉴
3. 문의 계약·팝업·브랜드센터 문의내역
4. 온보딩 workflow·중복 방지·브랜드센터 상태

공통 파일을 수정하는 셸과 브랜드센터 작업은 각 영역 구현 후 순차 통합한다.

## 9. 검증 수준

장시간 전체 테스트를 구현 중에 반복하지 않는다. 테스트가 구현보다 오래 걸리지 않도록 검증 비용을 변경 위험에 맞춘다.

- 각 영역은 변경된 계약과 핵심 상태 전환을 확인하는 짧은 focused test만 실행한다.
- 이미 통과한 무관한 테스트 묶음은 다시 실행하지 않는다.
- 실제 PostgreSQL, 전체 브라우저, 전체 migration 회귀는 작은 커밋마다 실행하지 않는다.
- TypeScript 빌드와 `git diff --check`를 통합 게이트로 실행한다.
- 전체 회귀와 실제 브라우저 검증은 병합·배포 직전 한 번만 수행한다.
- 느린 환경에서 테스트 하네스 timeout만 발생하면 기능 assertion 실패와 구분해 보고하며 반복 실행하지 않는다.
- 실제 운영 배포 전에는 인증·OAuth·세션·워크스페이스·브랜드 데이터가 변경되지 않는지 별도로 확인한다.

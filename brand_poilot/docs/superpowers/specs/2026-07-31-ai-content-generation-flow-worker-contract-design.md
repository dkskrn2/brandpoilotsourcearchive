## 2. 목표

콘텐츠 생성 워커가 신뢰할 수 있는 고정 입력만 사용하도록 생성 경계를 다시 정의한다.

신규 생성에 허용되는 정보는 다음과 같다.

1. 승인된 브랜드 코어
2. 사용자가 선택한 하나의 소재: 직접 입력 주제, URL 또는 레퍼런스
3. 마케팅성일 때 선택한 승인·활성 제품·서비스 하나
4. 검색 근거와 선택 레퍼런스의 고정 스냅샷
5. 브랜드센터의 스타일 이미지, 그중 선택한 아바타 역할 이미지, 필요한 첨부 이미지
6. 콘텐츠 지시문과 공통 이미지 지시문
7. 목적, 출력 형식, 채널, 비율을 포함한 출력 설정

Wiki ID, Wiki 본문, FAQ 데이터, 로고 파일과 로고 URL은 콘텐츠 생성 입력, 스냅샷, 워커 계약과 프롬프트에 포함하지 않는다.

## 3. 범위

### 3.1 포함

- 콘텐츠 설정, 구성안 선택, 최종 생성 화면
- 콘텐츠 제안 API와 제안 워커
- 콘텐츠 생성 오케스트레이션, 저장 스냅샷과 워커 계약
- 카드뉴스, 블로그, 마케팅 콘텐츠, 릴스 생성 워커 경로
- 이미지 생성 워커에 전달되는 버전 계약
- 1~5장 이미지의 부분 실패 재시도
- 릴스용 무음 FFmpeg 조립
- 신규 계약과 직접 연관된 화면·API·워커 테스트

### 3.2 제외

- 온보딩 워커
- DM 워커
- 게시 워커와 게시 도메인 변경
- Wiki·FAQ 기능 자체의 삭제 또는 마이그레이션
- 브랜드센터 스타일 데이터 모델 확장
- 오늘의 주제 수집 워커 구현
- 오디오 생성, 음악 선택과 음원 저장
- 로고 삽입 기능
- 관련 없는 리팩터링과 전체 테스트
- 운영 배포
- 가짜 오늘의 주제나 샘플 생성 결과

오늘의 주제는 화면에 `준비 중` 버튼으로 표시하되 선택할 수 없고, 현재 API 계약에서도 받지 않는다. 수집 워커와 데이터 계약은 별도 설계 후 연결한다.

## 4. 핵심 용어와 수량 계약

목적과 출력 형식은 서로 다른 축이다.

- 목적: `informational | marketing`
- 출력 형식: `card_news | blog | reel | marketing_content`

두 목적 모두 네 출력 형식을 사용할 수 있다. `marketing_content`는 목적이 아니라 이미지와 채널 카피를 묶는 출력 형식이다.

수량은 다음 세 값으로 분리한다.

- `proposalCount`: 항상 3
- `outputCount`: 항상 1
- `assetCount`
  - 카드뉴스·릴스·마케팅 콘텐츠: 구성안마다 LLM이 1~5 중 결정
  - 블로그: HTML은 항상 1개이며, 최종 작성 중 필요하다고 판단할 때만 이미지 0~5개

사용자는 최종 output 수를 선택하지 않는다. 신규 API 요청에서 `outputCount`가 1이 아니면 거부한다. 기존에 저장된 다중 output은 계속 읽고 다운로드하고, 기존 발행 지원 범위 안에서 발행할 수 있다.

## 5. 현재 구조에서 변경할 문제

현재 구조에는 이번 목표와 충돌하는 다음 동작이 있다.

- 제품·서비스 분석과 Wiki가 콘텐츠 소재에 포함된다.
- Wiki 스냅샷이 최종 생성 입력에 들어간다.
- 레퍼런스를 제안 생성 후 선택하여 제안 워커가 레퍼런스를 보지 못한다.
- 제안 워커가 정확히 3개가 아닌 2개 또는 3개를 반환할 수 있다.
- 정보성과 마케팅성의 출력 형식이 서로 다르게 제한된다.
- 채널이 활성·인증 상태와 무관하게 텍스트 중심으로 표시된다.
- 신규 최종 output이 1~3개일 수 있다.
- 블로그가 대표 이미지와 본문 이미지를 필수로 전제한다.
- 현재 릴스는 단일 장면, 장면당 7초, 음악과 AAC 오디오를 전제한다.

신규 버전 계약은 이 동작을 바꾸되 과거 결과 조회 계약은 유지한다.

## 6. 사용자 화면 흐름

현재 마법사의 큰 구조를 유지하고 내용을 세 단계로 재구성한다. 입력 항목을 지나치게 많은 화면으로 나누거나 모든 항목을 한 화면에 평면적으로 놓지 않는다.

### 6.1 1단계: 콘텐츠 설정

표시 순서는 다음과 같다.

1. 목적 선택
2. 소재 선택
3. 제품·서비스 선택
4. 추가 콘텐츠 지시문
5. 출력 형식
6. 채널 선택

#### 목적

- `정보성`
- `마케팅성`

정보성으로 전환하면 제품 선택 UI를 숨기고 메모리에 남은 제품 ID도 제거한다. API도 정보성 제품 입력을 별도로 거부한다.

#### 소재

소재는 주제와 레퍼런스 중 정확히 하나를 선택한다.

주제 탭:

- 직접 입력
- URL 입력
- 오늘의 주제: `준비 중`으로 비활성화

직접 입력과 URL을 동시에 보낼 수 없다. URL은 오케스트레이션 계층이 수집하고 고정 스냅샷으로 바꾼다.

레퍼런스 탭:

- 현재 브랜드와 같은 업종의 인기 레퍼런스 표시
- 기존 트렌드 탐색 기능을 이용한 검색
- 1~5개 선택
- 각 레퍼런스에 `planning`, `copy_pattern`, `visual_composition` 역할 지정

다른 브랜드 소유의 레퍼런스 ID는 API에서 거부한다. 이 단계에서 선택한 레퍼런스는 제안과 최종 생성 모두에 같은 스냅샷으로 사용한다. Wiki 선택 영역은 표시하지 않는다.

#### 제품·서비스

- 정보성: 영역을 표시하지 않고 `productId`는 반드시 `null`
- 마케팅성: 현재 브랜드에 속하고 승인·활성 상태인 제품·서비스 하나를 필수 선택

새 제품·서비스 분석은 콘텐츠 생성 화면에서 제거한다. 제품 사실은 브랜드센터의 승인된 제품·서비스 스냅샷에서만 가져온다.

#### 추가 콘텐츠 지시문

`contentInstruction`은 선택 입력이다.

- 구성안 3개 모두에 반영한다.
- 선택한 최종 콘텐츠에도 유지한다.
- 이미지에만 적용되는 `userImageInstruction`과 분리한다.

#### 출력 형식

- 카드뉴스
- 블로그
- 릴스
- 마케팅 콘텐츠

릴스 비율은 9:16로 고정한다. 카드뉴스와 마케팅 콘텐츠는 선택 채널과 호환되는 비율만 허용한다. 블로그는 HTML이 기본 산출물이므로 이미지 비율을 필수 입력으로 요구하지 않는다.

#### 채널

출력 형식을 선택한 뒤 다음 조건을 모두 만족하는 채널만 표시한다.

- 현재 브랜드에서 인증됨
- 활성 상태
- 선택 출력 형식을 지원함

채널은 텍스트 목록 대신 로고를 주 표시로 사용한다. 접근성 이름, 선택 상태와 툴팁은 유지한다. 채널은 정확히 하나만 선택한다. 형식 변경으로 선택 채널이 호환되지 않게 되면 선택을 해제한다. 사용 가능한 채널이 없으면 원인을 안내하고 구성안 생성을 차단한다.

#### 구성안 생성 버튼

다음 조건을 모두 만족할 때만 활성화한다.

- 목적 선택
- 유효한 소재 하나 선택
- 마케팅성이면 제품 하나 선택
- 출력 형식 선택
- 호환 채널 하나 선택

### 6.2 2단계: 구성안 선택

한 요청에서 이미지 없는 구성안 세 개를 표시한다.

공통 표시 정보:

- 제목과 콘텐츠 유형
- 한 줄 기획 의도
- `이 안의 차별점`
- 타깃
- 고객 질문 또는 상황
- 핵심 메시지
- 훅
- 선택 이유
- 검색 근거와 사용 레퍼런스
- 출력 형식과 채널 로고
- 순서별 개요

정보성 추가 정보:

- 사용자가 해결하려는 질문이나 문제
- 제공 가치
- 지금 다룰 이유
- 핵심 학습 포인트
- 검색 근거

정보성 proposal의 `informationalType`은 다음처럼 콘텐츠 구조를 구분한다.

- `problem_solution`: 문제 해결
- `how_to`: 방법 안내
- `checklist`: 체크리스트
- `comparison`: 비교·선택 기준
- `trend_insight`: 트렌드·인사이트
- `q_and_a`: 질문과 답변
- `myth_fact`: 오해와 사실

이 유형은 Wiki·FAQ 데이터 출처를 의미하지 않는다. LLM은 소재와 검색 근거에 맞는 유형을 선택하며, 세 안을 항상 서로 다른 유형으로 강제하지 않는다. 유형은 타깃, 상황, 질문, 소구점, 서사와 함께 사용할 수 있는 차별화 축 중 하나다.

마케팅성 추가 정보:

- 캠페인 목적
- 고객 상황과 니즈
- 선택 제품
- 고효율·고전환 가능성이 높은 타깃 세그먼트
- 제품의 강점과 한계
- 소구점
- 구매 장벽
- 메시지와 CTA

카드뉴스·릴스·마케팅 콘텐츠에는 각 안의 1~5장 수와 장면별 역할을 표시한다. 장수는 고정 규칙으로 계산하지 않고 각 구성안을 만든 LLM이 내용에 따라 선택한다. 비슷한 제목이나 말투만 다른 세 안은 허용하지 않으며 타깃, 상황, 질문, 소구점, 서사 중 유효한 축을 LLM이 골라 실질적으로 구분한다. 고정 A/B/C 템플릿은 사용하지 않는다.

선택한 구성안의 장수와 순서는 최종 생성까지 잠근다. 상세 기획 워커는 카피, 근거와 시각 방향을 보강할 수 있지만 장수와 순서를 바꿀 수 없다. 내부 추론이나 chain-of-thought는 화면에 표시하지 않는다.

#### 구성안 선택 후 이미지 설정

같은 단계의 하단에 다음을 표시한다.

- 자동 적용될 최신 승인 브랜드 스타일 이미지 목록
- 스타일 이미지 중 하나를 아바타 역할로 지정하는 선택 기능
- 필요한 기존 첨부 이미지 선택 또는 첨부
- 모든 생성 이미지에 공통 적용할 `userImageInstruction`

현재 브랜드 스타일은 등록 이미지로만 취급한다. 색상, 폰트, 메모를 신규 워커 계약에 넣지 않는다. 스타일 이미지가 없어도 안내 후 생성은 허용한다. 별도 아바타 라이브러리와 일회성 아바타 업로드는 사용하지 않는다. 아바타 ID는 반드시 현재 고정된 스타일 이미지 집합의 항목이어야 한다.

첨부 이미지는 `product_image`, `visual_reference`, `supporting_image` 역할로 정규화하고 현재 generation에 속한 업로드만 허용한다. 첨부 기능을 별도 아바타 업로드 통로로 사용하지 않는다.

레퍼런스는 1단계에서 이미 선택했으므로 이 단계에서 다시 선택하지 않는다. 블로그에서는 스타일·아바타·공통 이미지 지시가 블로그 워커가 이미지를 필요하다고 판단한 경우에만 적용된다고 안내한다.

### 6.3 3단계: 최종 생성과 결과

구성안 하나를 선택하면 최종 생성 버튼을 사용할 수 있다. 스타일 이미지 존재 여부, 아바타 지정과 공통 이미지 지시문은 필수 조건이 아니다.

최종 결과는 항상 콘텐츠 패키지 하나다.

- 카드뉴스: 이미지 1~5장, 캡션과 채널 메타데이터를 가진 패키지 하나
- 블로그: HTML 하나와 선택적 이미지 0~5장
- 릴스: 무음 MP4 하나, 첫 장면 커버와 채널 카피
- 마케팅 콘텐츠: 이미지 1~5장, 카피와 CTA를 가진 패키지 하나

기존 조회와 다운로드 기능을 유지한다. 기존 게시 기능이 지원하는 결과만 현재 게시 흐름을 사용한다. 미지원 조합은 발행 버튼을 숨기거나 비활성화하며 게시 워커는 수정하지 않는다.

## 7. 검색과 근거 수집

검색은 워커가 임의로 네트워크를 조회하는 방식이 아니라 오케스트레이션 계층이 수집하고 고정한 근거를 워커에 전달하는 방식으로 통제한다.

### 7.1 제안 생성 전

- 정보성: 온라인 검색을 수행한다.
- 마케팅성: 시장·고객 맥락이 필요하다고 판단될 때 자동 검색한다.
- URL 소재: 입력 URL 수집 결과를 먼저 고정하고 필요한 검색 근거를 추가한다.
- 레퍼런스 소재: 선택 레퍼런스 스냅샷과 필요한 검색 근거를 함께 고정한다.

마케팅 검색은 시장 상황, 고객 니즈, 구매 장벽과 최신 맥락에만 사용한다. 제품의 기능, 성능, 가격, 장점과 한계는 승인 제품 스냅샷만 사실 근거로 사용한다.

세 구성안은 같은 `researchEvidence` 스냅샷을 사용한다. 제안 워커 자체는 외부 URL을 가져오지 않는다.

### 7.2 블로그 보충 검색

선택 구성안을 블로그로 확장할 때 최신 근거나 설명이 부족하면 블로그 워커가 보충 검색 필요성을 반환할 수 있다. 오케스트레이션이 검색을 수행하고 결과를 고정한 뒤 같은 블로그 작업을 계속한다. 블로그 워커에 무제한 실시간 검색 권한을 주지 않는다.

실제 본문에 사용한 검색 출처만 본문 근처 링크와 하단 `참고자료`에 표시한다.

## 8. 버전 계약과 스냅샷

### 8.1 제안 요청

신규 제안 요청은 `content-orchestration.v2`를 사용한다.

```json
{
  "contractVersion": "content-orchestration.v2",
  "brandId": "<brand-id>",
  "purpose": "informational",
  "seed": {
    "kind": "topic_text",
    "title": "초보 사업자가 브랜드 메시지를 정리하는 방법"
  },
  "contentInstruction": "실무자가 바로 적용할 수 있도록 구성",
  "productId": null,
  "outputSettings": {
    "outputFormat": "card_news",
    "channelTargets": ["instagram"],
    "aspectRatio": "4:5",
    "outputCount": 1
  }
}
```

`seed`는 다음 판별 공용체 중 하나다.

- `{ kind: "topic_text", title }`
- `{ kind: "topic_url", url }`
- `{ kind: "reference", referenceIds }`

오늘의 주제 값은 현재 계약에 존재하지 않는다.

클라이언트는 브랜드 코어 본문, 제품 본문과 레퍼런스 본문을 보내지 않는다. ID와 사용자 입력만 보낸다. API가 소유권과 상태를 확인한 뒤 서버 저장소에서 본문을 읽는다.

### 8.2 제안 입력 스냅샷

검증이 끝나면 API가 `ProposalInputSnapshotV2`를 만든다.

- 승인 브랜드 코어와 `versionId`
- 정규화된 주제, URL 수집 결과 또는 레퍼런스 스냅샷
- `contentInstruction`
- 마케팅성 제품 스냅샷
- 검색 근거
- 목적과 출력 설정
- 생성 시각과 원본 버전 식별자

승인 브랜드 코어에는 콘텐츠 생성에 필요한 다음 항목만 포함한다.

- `companyOverview`
- `businessDescription`
- `primaryCategory`
- `detailedCategory`
- `primaryTarget`
- `differentiator`
- `coreAppeal`

제품 스냅샷에는 승인된 제품·서비스의 이름, 설명, 카테고리, 사실 기반 특징, 강점, 알려진 한계와 사용 가능한 제품 이미지만 포함한다.

### 8.3 제안 결과

`ContentProposalSetV2`는 다음을 보장한다.

- `proposals.length === 3`
- 세 proposal ID가 서로 다름
- 배치 공통 `researchEvidence`
- 세 안을 구분한 동적 차별화 근거
- 시각 출력 형식의 `assetCount`가 1~5
- `outline.length === assetCount`
- outline index가 1부터 연속

블로그 proposal은 글의 구조와 이미지 필요성 판단 기준을 제시하지만 이미지 수를 잠그지 않는다. 블로그 이미지 수는 최종 본문 작성 중 0~5로 결정한다.

### 8.4 최종 생성 입력

구성안을 선택한 뒤 API가 `content-generation-input.v3`을 만든다.

```json
{
  "contractVersion": "content-generation-input.v3",
  "brandCore": {
    "versionId": "<brand-core-version>",
    "companyOverview": "<approved-overview>",
    "businessDescription": "<approved-business-description>",
    "primaryCategory": "<primary-category>",
    "detailedCategory": "<detailed-category>",
    "primaryTarget": "<primary-target>",
    "differentiator": "<differentiator>",
    "coreAppeal": "<core-appeal>"
  },
  "subject": {
    "kind": "topic_text",
    "title": "초보 사업자가 브랜드 메시지를 정리하는 방법"
  },
  "contentInstruction": "실무자가 바로 적용할 수 있도록 구성",
  "product": null,
  "researchEvidence": [],
  "references": {
    "selected": [],
    "brandStyleImages": [],
    "avatarStyleImageId": null,
    "attachments": []
  },
  "selectedProposal": {
    "id": "<proposal-id>",
    "outputFormat": "card_news",
    "assetCount": 3,
    "outline": [
      { "index": 1, "role": "hook" },
      { "index": 2, "role": "explanation" },
      { "index": 3, "role": "summary" }
    ]
  },
  "userImageInstruction": "밝고 정돈된 편집 디자인",
  "outputSettings": {
    "purpose": "informational",
    "outputFormat": "card_news",
    "channelTargets": ["instagram"],
    "aspectRatio": "4:5",
    "outputCount": 1
  }
}
```

이 스냅샷은 제안 때 사용한 브랜드 코어, 제품, 선택 레퍼런스와 검색 근거를 그대로 유지한다. 최종 생성 시작 시에는 자격만 다시 확인한다.

- 브랜드 코어가 여전히 승인 상태인지 확인
- 마케팅 제품이 여전히 승인·활성 상태인지 확인
- 선택 레퍼런스가 여전히 사용 가능한지 확인

단순히 새 버전이 추가된 경우에는 선택 구성안과의 일관성을 위해 기존 스냅샷을 사용한다. 승인이 취소되거나 리소스를 사용할 수 없게 된 경우에는 최종 생성을 차단한다.

최종 시점에 최신 승인 브랜드 스타일 이미지 집합, 아바타 역할 선택과 공통 이미지 지시문을 추가한다. 최종 워커는 DB에서 브랜드·제품·Wiki·FAQ를 다시 조회하지 않는다.

### 8.5 금지 필드

신규 요청이나 워커 입력에 다음 값이 있으면 무시하지 않고 거부한다.

- `wikiItemIds`
- `wikiSnapshots`
- Wiki 본문
- `faqData`
- FAQ 질문·답변 본문
- 로고 파일, 로고 URL과 로고 배치 지시
- 정보성의 제품 ID 또는 제품 본문
- 클라이언트가 임의로 보낸 브랜드·제품·레퍼런스 본문

## 9. 워커 라우팅과 책임

신규 작업은 `outputFormat`을 실제 라우팅 기준으로 사용하고 `purpose`는 워커 내부의 정보성·마케팅성 전략을 고르는 기준으로 사용한다.

| 출력 형식 | 상세 기획 워커 | 후속 처리 |
| --- | --- | --- |
| `card_news` | 카드뉴스 워커 | 이미지 워커 |
| `blog` | 블로그 워커 | 필요할 때만 이미지 워커 |
| `reel` | 마케팅 워커 | 이미지 워커, FFmpeg |
| `marketing_content` | 마케팅 워커 | 이미지 워커 |

마케팅 워커라는 기존 이름은 저장·claim 호환성을 위해 유지하지만 목적 전용 워커로 해석하지 않는다. 릴스와 마케팅 콘텐츠를 처리하며 두 목적을 모두 지원한다.

기존 `content_type` 호환 매핑은 다음과 같다.

- `card_news` → `card_news`
- `blog` → `blog`
- `reel` → `marketing`
- `marketing_content` → `marketing`

신규 payload의 `outputFormat`이 세부 동작의 권위 있는 값이다.

### 9.1 콘텐츠 제안 워커

- 이미지 없는 구성안 정확히 3개 생성
- 목적별 proposal 구조 생성
- 세 안의 실질적 차이를 동적으로 선택
- 시각 형식별 1~5장 수와 순서 결정
- 빈 장면을 만들지 않고 각 장에 충분한 내용을 압축하도록 지시
- 같은 고정 검색·레퍼런스·제품 스냅샷 사용
- Wiki·FAQ·로고 미사용
- 외부 URL 직접 조회 금지

### 9.2 카드뉴스 워커

- 선택 proposal의 장수와 순서를 유지
- 카드별 제목, 본문, 근거, 시각 방향을 구체화
- 정보성과 마케팅성 모두 지원
- `ImageGenerationPackageV1` 생성
- 이미지 완료 뒤 캡션과 채널 메타데이터를 포함한 패키지 하나 완성

### 9.3 블로그 워커

- HTML을 기본 산출물로 생성
- 필요할 때만 이미지 계획 0~5개 생성
- 보충 검색 필요 여부를 명시적으로 반환
- 검색 결과가 필요하면 오케스트레이션이 고정한 뒤 이어서 작성
- 이미지 계획이 있으면 이미지 워커 결과 URL을 HTML에 삽입
- Wiki·FAQ·로고 미사용

### 9.4 마케팅 워커

- `reel`과 `marketing_content` 처리
- `purpose=informational`이면 정보 제공, 인지도와 참여 중심
- `purpose=marketing`이면 선택 제품, 전환, 장벽과 CTA 중심
- 선택 proposal의 장수와 순서를 유지
- 릴스의 장면 카피, 시각 방향, 캡션 생성
- 마케팅 콘텐츠의 이미지 계획, 채널 카피, 해시태그와 CTA 생성
- 이미지 생성 패키지 작성

### 9.5 이미지 워커

이미지 워커는 기획을 다시 하지 않고 확정된 자산만 렌더링한다.

- 장면 하나당 이미지 생성 호출 하나
- 정확한 index, 비율과 장수 유지
- 성공 장면을 재시도 중 다시 생성하지 않음
- 스타일 이미지, 아바타, 레퍼런스 역할과 공통 이미지 지시 적용
- 결과 이미지 검증 후 저장
- 릴스 장면이 모두 완성되면 FFmpeg 실행

## 10. 형식별 최종 계약

### 10.1 카드뉴스

- 이미지 1~5장
- 구성안에서 잠긴 장수와 순서 유지
- 각 장은 제목만 있는 빈약한 카드가 되지 않도록 충분한 정보를 담음
- 글자 가독성을 해치도록 한 장에 과도하게 밀어 넣지 않음
- 캡션, 해시태그와 필요한 CTA 포함
- 최종 콘텐츠 패키지는 하나

### 10.2 마케팅 콘텐츠

- 이미지 1~5장
- 채널에 바로 사용할 이미지와 카피 패키지
- 정보성 목적에서는 제품 없이 인지도·정보·참여 중심
- 마케팅성 목적에서는 승인 제품 하나와 전환 목적 중심
- 제품 관련 사실은 제품 스냅샷 안에서만 표현
- 최종 콘텐츠 패키지는 하나

### 10.3 릴스

- 세로 이미지 장면 1~5개
- 1080×1920
- 30fps
- H.264 MP4
- 오디오 입력과 오디오 스트림 없음
- 각 장면은 정확히 4초
- 짧은 페이드 전환은 각 장면의 4초 안에 포함
- 총 길이는 `sceneCount × 4초`
- 인코딩 결과는 목표 길이와 1프레임 이내에서 일치
- 첫 장면을 커버로 사용
- 선택 proposal의 장수와 순서 유지

현재 음악 조회, 볼륨, 오디오 페이드, AAC 필수 검증을 신규 릴스 경로에서 제거한다. FFmpeg 조립만 실패하면 성공 이미지를 유지하고 영상 조립만 다시 실행한다.

### 10.4 블로그

블로그는 이미지 콘텐츠가 아니라 HTML 콘텐츠다.

- 최종 HTML 하나
- `<article>` 안에 H1 하나
- H1 바로 다음에 구조적으로 구분되는 요약 영역
- 요약 영역은 정확히 세 문단
- 세 요약 문단의 합계는 300자 이내
- `<article>`의 정규화된 전체 표시 텍스트는 3,000~10,000자
- SEO와 GEO를 고려한 제목, 메타 제목, 메타 설명과 의미 있는 문서 구조
- 독자가 실제로 묻는 형태의 자연스러운 H2·H3
- 질문 직후 핵심 답을 먼저 제시
- 자연스러운 키워드 사용, 반복 공식과 키워드 채우기 금지
- 상투적인 AI 문구와 기계적인 동일 패턴 금지
- 실제 사용 출처 링크와 하단 `참고자료`
- 사용하지 않은 출처를 참고자료에 추가하지 않음
- 이미지가 도움이 될 때만 0~5장 생성
- 대표 이미지 필수 규칙 없음

실제·가상·합성 경험담, 1인칭 체험, 고객 경험 서사, 경험담 면책 문구를 요구하거나 생성하지 않는다. Q&A 형태의 소제목은 허용하지만 FAQ 데이터를 사용한다는 의미가 아니다.

## 11. 이미지 생성 패키지

이미지 워커에는 전체 최종 생성 계약 대신 `ImageGenerationPackageV1`만 전달한다.

필수 내용:

- `generationId`
- `outputFormat`
- `purpose`
- 잠긴 `assetCount`
- 연속된 장면 index와 장면별 시각 지시
- 선택 레퍼런스의 고정 스냅샷과 역할
- 최신 승인 브랜드 스타일 이미지
- 선택한 아바타 역할 스타일 이미지
- 필요한 제품 이미지와 첨부 이미지
- 모든 이미지에 공통 적용되는 `userImageInstruction`
- 비율과 채널
- 로고 금지 정책

선택 레퍼런스에는 원본 ID, 역할, 제목, 원본 URL, 캡처 시각, 필요한 텍스트·이미지, checksum을 보관한다. 워커에는 소유권 검증이 끝난 스냅샷만 전달한다.

이미지 지시 우선순위는 다음과 같다.

1. 사실, 출력 형식, 장수, 순서, 비율과 로고 금지 같은 강제 계약
2. 사용자의 공통 이미지 지시
3. 브랜드센터 스타일 이미지
4. 역할이 지정된 선택 레퍼런스
5. 장면별 시각 방향

공통 이미지 지시는 모든 생성 이미지에 적용하지만 proposal의 장수, 순서, 제품 사실과 로고 금지 규칙을 덮어쓸 수 없다.

모든 이미지 프롬프트에 다음을 명시한다.

- 로고, 워드마크, 심볼, 워터마크와 가짜 로고를 새로 만들지 않음
- 로고를 넣기 위한 빈 영역을 따로 만들지 않음
- 외부 레퍼런스의 로고를 복제하지 않음
- 선택한 실제 제품 사진이나 포장에 원래 인쇄된 로고는 지우지 않아도 됨

## 12. 검증과 보안

### 12.1 요청 검증

- 주제와 레퍼런스 동시 입력 거부
- 직접 입력과 URL 동시 입력 거부
- 정보성 제품 입력 거부
- 마케팅성 제품 누락 거부
- 다른 브랜드 제품·레퍼런스 ID 거부
- 비승인·비활성 제품 거부
- 사용할 수 없는 레퍼런스 거부
- 현재 브랜드 스타일 집합에 없는 아바타 ID 거부
- 현재 generation에 속하지 않은 첨부 이미지 거부
- 인증·활성·형식 호환 조건을 만족하지 않는 채널 거부
- 채널이 하나가 아닌 요청 거부
- 레퍼런스 1~5 범위 위반 거부
- 시각 asset 1~5 범위 위반 거부
- `outputCount !== 1` 거부
- Wiki·FAQ·로고와 클라이언트 제공 본문 거부

다른 브랜드 리소스는 실제 존재 여부를 노출하지 않고 공통 `RESOURCE_NOT_AVAILABLE` 오류로 응답한다.

### 12.2 워커 출력 검증

- proposal 정확히 3개
- proposal ID 중복 없음
- 형식별 필수 항목 존재
- 선언 장수와 outline·asset 배열 길이 일치
- index가 1부터 연속
- 상세 기획이 잠긴 장수·순서를 유지
- 블로그 길이, 요약, H1, 출처 구조 충족
- 이미지의 index, MIME, 해상도와 비율 일치
- 릴스의 코덱, 해상도, fps, 무음과 총 길이 충족

LLM의 구조 오류는 검증 오류 내용을 넣어 한 번만 자동 보정한다. 보정 후에도 실패하면 결과를 자르거나 임의 기본값으로 완료하지 않고 작업을 실패 처리한다.

## 13. 부분 실패, 재시도와 완료

최종 콘텐츠 패키지는 원자적으로 완료되지만 내부 이미지 장면은 개별 상태를 가진다.

- 자산 키는 `generationId + assetIndex`로 고정
- 성공 자산은 같은 생성 요청에서 재생성하지 않음
- 실패 자산만 동일한 이미지 패키지와 index로 재시도
- 모든 필수 자산이 성공하기 전에는 최종 패키지를 완료 처리하지 않음
- 부분 이미지는 내부 진행 상태로만 보관
- 자동 재시도 후 실패하면 전체 패키지를 실패 상태로 표시
- 사용자 재시도도 실패 자산부터 이어서 실행
- 릴스는 모든 장면이 성공한 뒤에만 FFmpeg 실행
- FFmpeg 실패 시 이미지 생성은 반복하지 않음
- 중복 시작 요청은 기존 idempotency key의 generation을 반환

블로그는 HTML 검증과 필요한 이미지 삽입이 모두 성공해야 완료한다. 이미지가 필요 없다고 판단된 블로그는 이미지 0장으로 정상 완료할 수 있다.

## 14. 기존 결과와 발행 호환

- 신규 생성 쓰기만 `content-orchestration.v2`, `ContentProposalSetV2`, `content-generation-input.v3`, `ImageGenerationPackageV1` 사용
- 기존 v1/v2 저장 결과는 기존 parser로 계속 읽음
- 기존 결과 데이터와 Wiki 스냅샷을 마이그레이션하거나 삭제하지 않음
- 기존 결과 조회, 새로고침 후 상태 복구와 다운로드 유지
- 현재 지원되는 발행 결과는 기존 발행 흐름 유지
- 게시 워커와 게시 계약은 수정하지 않음
- 신규 미지원 형식은 생성·조회·다운로드를 허용하고 발행 UI만 숨기거나 비활성화
- 기존 이미지 워커 계약은 버전으로 분기하고 신규 이미지 패키지 경로만 확장
- API나 워커 실패를 샘플 proposal, 샘플 이미지 또는 mock 결과로 대체하지 않음

## 16. 로컬 검증

전체 테스트가 아니라 수정한 파일과 직접 관련된 테스트만 실행한다.

### 16.1 화면

- 정보성에서 제품·Wiki가 보이지 않음
- 마케팅성에서 승인·활성 제품 하나가 필수로 보임
- 주제와 레퍼런스가 상호 배타적임
- 오늘의 주제 버튼은 보이지만 비활성임
- 출력 형식 네 개가 두 목적 모두에 표시됨
- 인증·활성·형식 호환 채널만 로고로 표시됨
- 채널 하나만 선택 가능
- 입력 조건에 따라 구성안 생성 버튼이 활성·비활성화됨
- 구성안 정확히 세 개와 차별점·장수·개요가 표시됨
- 구성안 선택 후 스타일, 아바타와 공통 이미지 지시를 사용할 수 있음

### 16.2 API와 저장소

- 정보성 제품 요청 거부
- 마케팅성 제품 누락 요청 거부
- 다른 브랜드 제품·레퍼런스 요청 거부
- Wiki·FAQ·로고 필드 요청 거부
- 채널 개수와 호환성 위반 거부
- `outputCount` 1 외의 요청 거부
- 제안과 최종 생성에 같은 브랜드 코어·제품·레퍼런스·검색 스냅샷 사용
- 신규 워커 payload에 Wiki·FAQ·로고가 없음
- 기존 결과 조회와 기존 발행 지원 결과가 계속 동작

### 16.3 워커

- 제안 워커가 정확히 세 proposal 반환
- 시각 proposal마다 1~5장과 연속 outline 반환
- 카드뉴스·마케팅 워커가 잠긴 장수와 순서를 유지
- 블로그가 HTML 하나, 3줄·300자 요약, 3,000~10,000자와 출처 규칙 충족
- 블로그가 이미지 0장으로도 정상 완료
- 스타일 이미지, 아바타, 레퍼런스 역할과 공통 이미지 지시가 이미지 워커 입력에 전달
- 이미지 워커가 정확한 장수와 순서 생성
- 일부 장면 실패 시 실패 장면만 재시도
- 로고 금지 지시가 모든 이미지 프롬프트에 포함

### 16.4 릴스

최소 1장과 최대 5장 사례를 로컬 FFmpeg로 직접 검증한다.

- 1080×1920
- 30fps
- H.264
- 오디오 스트림 없음
- 1장은 4초
- 5장은 20초
- 전환을 포함해 목표 길이와 1프레임 이내
- 첫 장면 커버 유지

로컬 검증 결과를 보고한 뒤 멈춘다. 운영 배포는 사용자의 별도 승인을 받은 후에만 수행한다.

## 17. 완료 조건

- 정보성 화면과 요청에 제품·Wiki가 없음
- 마케팅성 제안과 최종 생성에 승인·활성 제품 하나가 필수
- 주제 또는 레퍼런스 중 하나만 사용
- 레퍼런스가 제안 전에 선택되어 제안과 최종 생성에 같은 스냅샷으로 전달
- 정보성은 온라인 검색, 마케팅성은 필요 시 자동 검색을 구성안 생성 전에 수행
- proposal이 이미지 없이 정확히 세 개 생성되고 실질적으로 구분됨
- 사용자가 proposal 하나를 선택하고 최종 콘텐츠 패키지 하나를 생성
- 카드뉴스·릴스·마케팅 콘텐츠의 1~5장 수를 LLM이 제안별로 결정
- 블로그는 HTML 중심이며 이미지는 선택 사항
- 릴스는 장면당 4초, 총 `장면 수 × 4초`, 무음
- 브랜드 스타일 이미지, 아바타 역할 이미지, 선택 레퍼런스와 공통 이미지 지시가 이미지 패키지에 포함
- 어떤 신규 요청이나 워커에도 Wiki·FAQ·로고 데이터가 전달되지 않음
- 실패 장면만 재시도하고 성공 장면은 유지
- 다른 브랜드 제품과 레퍼런스를 거부
- 기존 결과 조회·다운로드·지원되는 발행 흐름이 유지
- 관련 파일의 직접 테스트와 로컬 확인만 수행
- 별도 승인 없이 운영 배포하지 않음
